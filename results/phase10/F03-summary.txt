OBSERVATIONS:

1. TCP masks 1% packet loss almost completely for HTTP. The median and
   p95 of the affected path are statistically unchanged. TCP
   retransmits the lost packets transparently.

2. The one signature of the loss is the tail: a single HTTP request
   observed at 1152 ms, consistent with the TCP minimum retransmission
   timeout (~1 s). This is exactly what a lost packet looks like at the
   application layer.

3. Zero HTTP errors on both paths. Even at 1% loss, TCP delivered every
   request successfully. This is expected behavior and is important to
   document: standard HTTP probes cannot directly measure packet loss
   when TCP retransmission hides it.

4. The central path's mild increase (+14 ms p50, +40 ms p95 during the
   fault window) is within normal variance for this single-host
   software testbed and is not evidence of cross-path interference.

5. The recovery window (p50 136 ms) is identical to baseline (p50 138 ms).

6. Both PDU sessions and the UE registration were unaffected.

CLEANUP:
- ogstun2 qdisc restored to fq_codel (default)
- No persistent rules left behind

CONCLUSION:
F03 demonstrates that 1% packet loss on a single UPF egress has almost
no effect on TCP-based HTTP metrics except for a single
retransmission-timeout spike in the tail. To measure packet loss
directly, one should use a UDP probe (the URLLC echo client). The HTTP
probe shows that TCP recovers from loss but at the cost of tail
latency. Both observations are legitimate and together they explain
why resilience testing must use multiple measurement protocols.
